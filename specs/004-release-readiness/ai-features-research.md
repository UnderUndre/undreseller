### 1. Физический тупик: Локальные LLM на VPS ≤500 МБ RAM

Утверждение: *«Локальный embedding search... Модель Qwen, Gemma, Phi на VPS. Данные не уходят наружу»*.

**Level 1 Hardware Factcheck:**
- **Текущий бюджет VPS:** Лимит RSS ≤ 500 МБ.
- **Базовый стек в памяти:**
- Next.js 15 (Node.js runtime в production SSR): ~130–180 МБ RSS.
- PostgreSQL инстанс (минимальные `shared_buffers` + соединения): ~80–120 МБ RSS.
- Два бота grammY (Long Polling / Webhooks) + Inngest runner: ~70–100 МБ RSS.
- **Итого база:** ~280–400 МБ RSS.
- **Свободный остаток памяти на хосте:** **100–150 МБ максимум.**

- **Аппетиты локальных моделей (Level 1):**
- Минимальный рантайм `llama.cpp` / `Ollama`: сам процесс демона берет от 50 до 150 МБ.
- Самая компактная квантованная модель на рынке — **Qwen 2.5 0.5B (Q4_K_M)**: размер файла весов ~350–390 МБ. Для загрузки контекста (KV Cache на 2048 токенов) требуется суммарно **не менее 600–750 МБ RAM** только под инференс.
- Модели уровня **Phi-3-mini (3.8B)** или **Gemma-2-2B** в 4-битном квантовании требуют **от 1.8 до 2.6 ГБ чистой памяти**.
- Даже микроскопическая модель векторных представлений `all-MiniLM-L6-v2` (ONNX Runtime) при инициализации аллоцирует ~120–180 МБ.

**Вердикт:**
Попытка запустить **любой** локальный инференс текста или эмбеддингов на этой машине гарантированно вызовет срабатывание **Linux OOM Killer** с мгновенным падением базы PostgreSQL или Node.js.

> *Вывод:* Концепция «Local LLM on VPS» для данного профиля железа — **физически невозможна**. Либо апгрейд тарифа VPS до $30–50/мес (минимум 8–16 ГБ RAM под CPU-инференс со скоростью 3 токена/сек), либо только внешние Cloud API.

### 2. Подмена понятий: Исследование операций (OR) вместо LLM

Утверждение: *«AI Scheduling Engine: Any Available Staff, Smart Slot Optimization, уплотнение расписания»*.

Это классическая ошибка эпохи AI-хайпа: **решать детерминированную математическую задачу через вероятностную языковую модель**.

- **В чем суть задачи:** У вас есть временная шкала (09:00–21:00) и отрезки разной длины с буферами. Задача размещения записи так, чтобы минимизировать «дырки» менее 30 минут — это классическая **одномерная задача упаковки (1D Bin Packing / Interval Scheduling)**.
- **Алгоритмическое решение:**
Жадный алгоритм (Greedy Heuristic) или динамическое программирование на чистом TypeScript:
```typescript
// Детерминированный штраф за фрагментацию расписания
function calculateGapPenalty(slotStart: Date, duration: number, existingSlots: Slot[]): number {
const leftGap = getLeftGapMinutes(slotStart, existingSlots);
const rightGap = getRightGapMinutes(slotStart, duration, existingSlots);
// Штрафуем дыры, в которые невозможно втиснуть минимальную услугу (например, < 30 мин)
let penalty = 0;
if (leftGap > 0 && leftGap < 30) penalty += 100;
if (rightGap > 0 && rightGap < 30) penalty += 100;
return penalty;
}
```
- **Сравнение подходов:**
- *TypeScript-алгоритм:* 0 токенов, 0.2 миллисекунды выполнения, 0 МБ дополнительной памяти, 100% математическая гарантия отсутствия овербукинга.
- *LLM:* $0.002 за запрос, задержка 1.5–3 секунды, риск галлюцинации таймстампов и наложения записей друг на друга.

> *Вывод:* Умное уплотнение слотов и «Any Available Staff» — это **P1 фича чистой дискретной математики**, а не AI. Называть её в маркетинге можно «Smart AI Engine», но писать ее нужно жестким кодом без единого вызова нейросетей.

### 3. Разбор сценария «AI Waitlist + Auto-Rebooking»

Идея спасения отмен через лист ожидания — действительно **золотая жила по окупаемости (ROI)**. Но давайте снимем розовые очки с того, как она реализуется.

**Как это работает без AI (MVP / Table Stakes):**
1. В 15:40 клиент отменяет запись на 17:00.
2. Inngest триггерит job по событию `booking.cancelled`.
3. SQL-запрос достает первых 3 клиентов из таблицы `Waitlist` с фильтром по дате и услуге.
4. Бот B1 отправляет им push: *«Освободилось окно на 17:00! Кто первый нажмет кнопку — забирает слот»*.
5. Первый кликнувший получает бронь (через атомарный `UPDATE WHERE status = 'HELD'`).

**Где здесь РЕАЛЬНО нужен AI:**
AI нужен **только** на этапе входящей обработки естественного языка, когда клиент в чате пишет человеку или боту свободным текстом:
*«Слушай, если на этой неделе после работы у Ани что-то освободится на брови, маякни мне»*.

- Регулярными выражениями это не распарсить.
- **Вот тут работает Cloud LLM (OpenAI gpt-4o-mini / Anthropic Claude 3.5 Haiku):**
Промпт с Function Calling / Structured Outputs извлекает JSON:
`{ "master": "Аня", "service": "brows", "preferred_time": "after_18:00", "days": ["mon", "tue", "wed", "thu", "fri"] }`
и кладет структурированную запись в PostgreSQL.
- Потребление ресурсов VPS: **0 МБ RAM**, стоимость запроса: **$0.00015**.

### 4. GDPR и приватность: Миф о необходимости On-Premise для салонов

Утверждение: *«Клиенты скажут: не хочу отправлять данные клиентов в OpenAI... аргументы приватности и контроля данных»*.

**Level 1 Legal & Compliance Reality (GDPR / DPA):**
1. В ЕС и Великобритании малый бизнес (барбершопы, спа, студии) массово использует облачные SaaS (Fresha, Treatwell, Phorest, Square). Ни один барбер не держит локальный сервер.
2. Согласно **GDPR Article 28**, передача персональных данных стороннему обработчику (Sub-processor) законна при наличии **Data Processing Addendum (DPA)** со Стандартными договорными условиями (SCCs).
3. У OpenAI, Anthropic и Google Cloud подписанный DPA входит в публичную оферту API. По условиям их API-соглашений данные клиентов **не используются для дообучения моделей**.
4. Достаточно не передавать в промпт фамилию, телефон и платежные данные.
*Вместо:* `Запиши Ивана Иванова (+49170123456) на массаж`
*Передавать в LLM:* `Intent extraction: "Запиши на массаж завтра вечером" -> { intent: "book", service: "massage", date: "tomorrow_evening" }`.
Номер телефона привязывается локально в PostgreSQL по `chat_id` Telegram. Личные данные наружу вообще не выходят.

- С KV-cache (даже на 4–8k токенов) + runtime overhead (llama.cpp / Ollama daemon) суммарно **1–2.6+ GB** в зависимости от источника и контекста.  
- Ollama официально: минимум ~8 GB RAM для 7B, для 1–3B комфортно 8 GB системы.  
- На VPS с жёстким ≤500 MB RSS (Next.js + Postgres + два grammY + Inngest уже занимают большую часть) любой локальный инференс → OOM Killer.

**Вердикт:** Local LLM / embeddings на текущем железе — запрещено архитектурой. Только Cloud API (gpt-4o-mini, Gemini Flash, Claude Haiku и т.п.) или апгрейд VPS. Абстракция `AI_PROVIDER` (openai / anthropic / gemini / ollama / openai-compatible) — правильный ход на будущее, но ollama-ветка сейчас мёртвая.

## 3. Smart Slot Packing / Any Available Staff+

Ресерч прав: это **не задача для LLM**.

Уплотнение расписания, минимизация дыр < минимальной услуги, выбор «любого свободного мастера» с учётом буферов — классическая дискретная оптимизация (interval scheduling / greedy / динамическое программирование).  
Детерминированный TypeScript/SQL:
- 0 токенов,
- микросекунды,
- 100% гарантия отсутствия овербукинга,
- 0 дополнительной RAM.

LLM здесь — антипаттерн (задержка, стоимость, риск галлюцинации слотов). Можно называть в маркетинге «Smart Scheduling Engine», но писать кодом. **P1, не AI.**

## 4. AI Waitlist + Auto-Rebooking

Самый сильный денежный сигнал.

Многие платформы уже имеют waitlist, но **автоматическая рассылка при отмене** часто отсутствует или слабая (Booksy/Vagaro/Fresha — есть waitlist, но не всегда мгновенный auto-text/push).  
Реализация без LLM (MVP):
1. `booking.cancelled` → Inngest job.
2. SQL: выбрать N клиентов из Waitlist по услуге/дате/мастеру.
3. Telegram (или email) с inline-кнопкой «Забрать слот».
4. Атомарный UPDATE в HELD.

LLM нужен **только** если клиент пишет свободным текстом («если после работы у Ани освободится на брови — маякни»). Тогда Cloud API + structured outputs → JSON в Postgres. Стоимость копеечная, RAM на VPS ≈ 0.

**Вердикт:** Waitlist fill — P1 (код). NL-parsing в waitlist — P2 (Cloud LLM).

## 5. No-Show Prediction

Продаётся активно.  
Реалистично:
- На MVP данных нет → P3.
- Когда появятся сотни/тысячи записей — простая логистическая регрессия / правила по фичам (новый клиент, история отмен, lead time, день недели, услуга) + extra reminder / депозит. Не обязательно LLM.

## 6. Privacy / GDPR / «не хочу в OpenAI»

Миф для барбера/массажиста.

- Малый бизнес массово сидит на облачных Fresha/Booksy/Square.  
- OpenAI API: DPA существует, данные API **не используются для обучения** по умолчанию (с марта 2023). Retention ~30 дней для abuse monitoring, есть Zero Data Retention по запросу.  
- Достаточно не слать в промпт ФИО, телефон, адрес — только intent. Привязка к `chat_id` остаётся в Postgres.

On-prem / local LLM для типичного соло-мастера **не требуется**. Аргумент «privacy» работает для клиник/юристов, но не для beauty/tutoring/repairs в текущем профиле.

## Итоговый вердикт

Ресерч по продуктовой ценности AI **в целом верен**: рынок покупает автоматизацию ресепшна, заполнение отмен и снижение no-show, а не генераторы текста.  

Критические поправки под ваше железо и соло:
1. Локальный AI на ≤500 MB — физически невозможен. Только Cloud API.
2. Уплотнение слотов и базовый Waitlist — детерминированный код, не LLM.
3. LLM имеет смысл только для NL-интерфейса (Telegram AI receptionist / парсинг свободного текста в waitlist).
4. Сначала закрыть P0 из предыдущих аудитов (Slot Hold FSM, IPN, in-call адрес, notification reliability), потом одну денежную фичу: **Waitlist + auto-fill**.

Bayesian confidence по рыночному спросу на receptionist/waitlist/no-show: ~75–80%. По невозможности local LLM на текущем VPS: ~95%.​‌

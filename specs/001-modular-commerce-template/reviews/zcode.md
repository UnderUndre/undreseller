## Summary

Track 1 vs frozen Medusa (Track 2) is the one decision that is actually nailed down, and the 500 MB RAM fence matches the business plan. The rest of the spec is a menu of payment rails, search strategies, and order states that do not survive contact with concurrency, Meta policy, or the $4,900 / 5–7 day promise. `analyze.md` scored 100% coverage because every FR has a task id; that is not the same as the task being implementable. The headline cracks are a booking lock that cannot be correct on the published schema, a payment state machine that contradicts itself, and a P1 catalog with no admin write path.

## Findings

| ID | Severity | Area | Finding | Recommendation |
| --- | --- | --- | --- | --- |
| F1 | CRITICAL | Data model / booking | `BookingSlot` is one row per appointment (`orderId @unique`, `lockedUntil`, `isBooked`). Two shoppers opening the same free window create **two rows**, so `SELECT … FOR UPDATE` locks nothing shared. There is no exclusion constraint on `(itemId, tstzrange(startTime, endTime))`, no working-hours table, and no sweep that expires `lockedUntil`. FR-03 and US1 AC2 ("slot blocked for 15 minutes, no overbooking") are not realizable on this schema. | Model availability as generated windows (or a range exclusion constraint) plus one reservation row. Add a unique/exclusion constraint so a second lock fails. Add an expiry path (`lockedUntil < now()` → free) before PAID. Put the constraint in T-002, not in a comment. |
| F2 | CRITICAL | Payments / state machine | US1 creates `Order` as `PENDING`. US5 independent test moves `PENDING → CONFIRMED` on payment. FR-13 moves `Order` to `PAID` and the slot to a status `PERMANENT_BOOKED` that **does not exist** on `BookingSlot` (only `isBooked` / `lockedUntil`). `CONFIRMED` is never defined vs `PAID`. T-019 only says `PENDING → PAID`. A client who locks a slot and never pays holds it until a human notices. Stock on `Item.stock` is never decremented in any task, so two PRODUCT checkouts oversell. | One transition table: `PENDING` (lock held) → `PAID` (webhook, idempotent) → optional `FULFILLED`; `CANCELLED` releases lock and restores stock. Delete `PERMANENT_BOOKED` or add the column. Define who sets `CONFIRMED`. Add stock decrement + compensating release to T-019, with a test for double webhook **and** for abandoned lock. |
| F3 | HIGH | Requirements gap / admin | FR-01 is "Product & Service CRUD". Tasks cover schema (T-002) and a public card (T-005). There is no admin auth, no write API, no seed, no image upload. `EscalationTicket` has no admin UI. NFR-04 says autoresponder copy is editable "через конфигурацию/админку" — T-003 is a TS file, which **is** a rebuild. A 5–7 day client delivery cannot change a price, a greeting, or a knowledge PDF without a developer. | Either cut FR-01 to "seed + config, no admin" and say so in the SOW, or add an admin lane: one role, Zod-validated mutations, image storage, and a non-rebuild path for greeting/knowledge (or document that copy changes ship as a git commit). Do not leave CRUD as a word. |
| F4 | HIGH | Failure modes / async | NFR-02: webhooks return 200 in < 1.5 s; AI (< 3 s, US4) and invoice generation run **asynchronously**. Plan §2.5 and T-022 log failures. There is no queue. Business plan v18.3 §1.1 forbids n8n inside Sprint B and names Trigger.dev v3 / Inngest. The plan never picks one. On a single Node process, "async" means the request dies with the process: Telegram retries the webhook, WhatsApp does not reliably, the customer sees silence, and the in-memory rate limiter (NFR-03) resets on every deploy so the 10 msg/min cap is theater under 2 replicas. | Name the job runner (Inngest route or Trigger.dev — already the house standard) in plan §2. Ack the webhook only after the job id is durable. Specify retry, dead-letter, and what the user sees when the LLM times out. State the process model: one container, so LRU is acceptable; if horizontal, the limiter is wrong. |
| F5 | HIGH | Security / PII / PCI | `Order` stores `customerPhone`, `customerEmail`, `customerTgId` in the same database as the catalog, with no retention, no encryption note, and no log redaction. T-022 ships "structured JSON telemetry" of webhook failures — payment payloads and `initData` will land in logs unless a denylist exists. US2 AC3 checks `initData` HMAC but no task owns it (T-008 is theme/SDK only; analyze mapped FR-05 onto that UI task). Checkout (T-020) offers a "Fiat link" while Stripe/Paddle/YooKassa have **zero** tasks: no webhook, no signature, no idempotency. Card data must not touch this app; the spec does not say the fiat rail is a hosted Checkout URL only. | Add a task for `initData` max-age + HMAC (FR-05), separate from the theme provider. Log denylist: tokens, `initData`, phone, email, payment body. Fiat = hosted Checkout / MoR redirect only; raw PAN never in this process. Pick **one** fiat provider or mark fiat as out of scope for v1. State retention (e.g. phone/email deleted N days after `CANCELLED`). |
| F6 | HIGH | Commercial / scope vs $4,900 | Hero SKU in v18.3 is **$4,900 flat, 14 calendar days**, scope knife = 2 roles, 1 business process, **1 external API**. This spec's own summary promises a client instance in **5–7 working days**, then the plan spends 9 days building Stars + NOWPayments + TON Connect + Stripe/Paddle/YooKassa + WhatsApp + RAG + catalog + booking. Phase 5 "packaging docs" (T-025) is not the business plan's Day-14 live onboarding (client pastes prod keys, $1 charge, webhooks verified before escrow release) and not the 7-day P1/P2 bugfix SLA. v16.0 in `undreseller/docs/` still freezes Medusa at $15k MRR and prices the tripwire at $1,500–$2,500; v18.3 says 10-sale Demand Gate at $350–$490 and freezes Medusa for Phase A. The spec cites v18.3 and does not notice the fork. | Freeze a v1 rail set in the spec: e.g. Stars **or** one crypto gateway, plus one MoR link. Move the other rails to Phase 2 backlog at $100/h. Add a task (or an explicit non-goal) for the Day-14 onboarding script. Add a one-line note that `undreseller/docs/undreseller-business-plan.md` v16.0 is not the commercial source; v18.3 is. Do not sell 5–7 days and schedule 9. |
| F7 | HIGH | Edge cases / messengers | US3 cooldown is "1 autoresponse per phone per 24 h". Gate 3 tests "two messages in 10 seconds". Neither is Meta policy. Outside the 24 h customer-care window, WhatsApp Cloud API only delivers **pre-approved templates**; a free-form greeting 404s or 131047s and the spec calls that "log and don't crash" (US3 AC3) — the lead gets nothing. Telegram: no `my_chat_member` handler, so a blocked bot keeps "replying" into the void. AI: FR-08 fixes chunk 500/50 but plan §2.1 also allows stuffing the whole doc into the prompt; T-014/T-015 do not say which, and there is no eval set for prompt injection beyond the sentence "isolated from jailbreaks". PDF parse of a client upload is an untrusted parser in-process (DoS / bomb) with no size cap. | v1 WhatsApp = one approved template + `hub.challenge` + signature, and a written failure when Meta rejects it. Pick BM25 **or** full-context, not both. Cap upload size and page count; parse outside the request path. Add 5 injection fixtures to the AI gate (ignore-previous, system-prompt exfil, off-topic, empty base, oversized question). |
| F8 | MEDIUM | Schema / expand-contract | T-002 asks for a `down.sql` and plan §2.4 says migrations avoid blocking locks. The published Prisma schema is greenfield (no ALTER, no `NOT NULL` added to a live table), so expand/contract is N/A **for v1**. It becomes a lie on the second client who already has orders: `down.sql` that `DROP TABLE` is not a rollback, and there is no online-index task, no lock timeout, and no backfill. `DIRECT_URL` is in the schema and T-004, but nothing says runtime uses the pooler and migrations use direct — the 002 review already caught the inverse bug. | State "v1 is create-only; expand/contract starts at the first migration after a client is live". `down.sql` restores the previous schema, it does not drop production orders. Document `DATABASE_URL` = pooled runtime, `DIRECT_URL` = migrate only. |
| F9 | MEDIUM | Ops / DR | No RPO/RTO, no backup, no health endpoint, no restore task. Business plan Sprint A already pays for Restic; this template's orders and slot locks are the thing a client will ask to restore. RAM gate disagrees with itself: NFR-01 ≤ 500 MB, Gate 1 ≤ 450 MB, T-023 ≤ 500 MB. Single-process LLM + `pdf-parse` + Next.js can pass an idle `docker stats` and die on the first real PDF. | One number. Add `GET /api/health` (db ping, no secrets) and a backup note: inherit the host Restic job, RPO = whatever that job already is, say it out loud. Bench with a concurrent webhook + one LLM call + one PDF index, not an empty homepage. |
| F10 | MEDIUM | Consistency / i18n / money | `price Decimal(10,2)` for Telegram Stars (integer XTR) will round. Currency default USD while YooKassa clients are RUB; no minor-unit rule. Crypto "tolerance < 1%" (US5 AC2) does not say who eats the difference or what happens at 1.1%. Plan tree has `apps/commerce-starter/` **or** "undreseller modular store" — tasks use repo-root paths (`app/`, `prisma/`). `tsvector` is promised in spec §2.3 and absent from the Prisma models. No timezone on slots (shop in Yerevan, client in US). No locale for the greeting. | Store money as integer minor units (or `Decimal` + currency exponent). Stars = integer XTR, not decimal USD. Pick the app root in one sentence. Add `shopTimezone` to config and generate slots in that zone. Drop `tsvector` or add the column and a GIN index to T-002. |
| F11 | LOW | Constitution lens | Principle VI is not violated: analyze PASS is present; this file is one external review, not the second. Principle VII tag is applied by the snapshot script, not by the spec text. Principles I–V and VIII govern `underoute-clai`, not this commerce template — no false CRITICAL. Principle IX: artifacts sit on `main` of the `undreseller` repo, not on a `specs/003-…` planning branch. That is a process miss, not a design flaw in the shop. | Do not block implement on Principle IX alone. Next planning wave should branch `specs/003-modular-commerce-template` before more edits, per constitution. |
| F12 | LOW | Stakeholder language | "Zero-downtime webhook SLA", "Prompt Firewall", "Zero-Ops" read as production guarantees. They are latency hopes plus a system prompt. A non-technical buyer will hear "the bot never lies and the shop never goes down". | Rename to measurable checks already in the gates (403 on bad signature, escalation row when the answer is not in the file). Keep the poetry out of the SOW. |

## Alternative approaches considered

- **Cal.com / Cal.diy for the slot grid** instead of a homegrown `BookingSlot`. The house stack already runs Cal.com in Sprint A. A service-booking client does not need a second scheduler with a broken lock. Worth a one-paragraph "considered and rejected" — rejected only if the Mini App must stay one origin and Cal's RAM blows the 500 MB fence.
- **Chatwoot as the WhatsApp edge** (spec §2.1 already says "or Chatwoot") instead of a bespoke cooldown table. Chatwoot already has the 24 h window, templates, and an inbox. Custom webhook + `MessengerContact` reimplements the part Meta will ban you for getting wrong.
- **One payment rail in v1** (Stars for digital, or a single MoR link). TON Connect *and* NOWPayments *and* a raw tx-hash watcher is three custody stories. The spec forbids server-side private keys (good) and then still offers "direct wallet address + hash check", which is support load, not a rail.
- **Postgres FTS only**, delete the "or stuff 8k tokens" branch. Two retrieval designs means the eval gate cannot fail.
